# Decisions (append-only)

Format: `## D<n> — title (date)` then Context / Decision / Consequence, ≤6 lines.

## D1 — Passkeys, not custom face recognition (2026-10-28)
Context: need human-in-the-loop biometric approval. Decision: WebAuthn platform authenticator (Face ID / fingerprint / Windows Hello), userVerification required. Consequence: no biometric data leaves the device; phishing-resistant; needs HTTPS + real device for demo.

## D2 — Approval bound to cart hash (2026-10-28)
Decision: WebAuthn challenge = base64url(SHA-256(JCS(cartApproval))). Consequence: any change to amount/items/address/merchant after approval invalidates the signature; merchant verifies independently against the registry public key.

## D3 — JCS + Ed25519 for agent payloads (2026-10-28)
Decision: RFC 8785 canonical JSON, Ed25519 via node:crypto. Consequence: deterministic hashes across services; small, fast signatures.

## D4 — Authorize then capture (2026-10-28)
Decision: PayPal intent AUTHORIZE; capture only after fulfillment checks; void on failure. Consequence: money held, not taken, until trust + fulfillment confirmed.

## D5 — Trust registry as shared tables (2026-10-28)
Decision: registry tables in the shared Postgres, seeded by script; pitched as PayPal-operated in production. Consequence: simple for the hackathon; documented limitation.

## D6 — LLM is escalate-only (2026-10-28)
Decision: LLM output never sets amounts or grants approval; risk inspector can only return step-up or block. Consequence: prompt injection cannot cause an unauthorized payment.

## D8 — No Docker; Neon Postgres (2026-10-28)
Context: no Docker on the dev machine. Decision: hosted Neon Postgres, `dev` branch for local work and tests, `main` for the Render deploy; Prisma `directUrl` for migrations. Consequence: needs internet to run locally; keep the production branch alive through judging (1–15 Dec).

## D7 — Vault vs per-order approval (2026-10-29)
Result: vault spike **SUCCESS** in sandbox. The user approves on PayPal once (save-with-purchase: `attributes.vault { store_in_vault: ON_SUCCESS, usage_type: MERCHANT, customer_type: CONSUMER }`); the `/authorize` response returns the vault id with status VAULTED. Later `intent: AUTHORIZE` orders with `payment_source.paypal.vault_id` come back COMPLETED with the authorization already created — no redirect, no `stored_credential` needed. Decision: agent payments use the saved PayPal wallet (vault id stored per user, server-side only); the passkey approval of the cart hash is the per-order consent. Per-order PayPal approval stays as the fallback if a vault id is missing or revoked. Consequence: needs US sandbox accounts (an India-country Business account rejected USD); the vault id is a reusable payment credential — never log or expose it in full.

## D9 — Toolchain versions (2026-10-29)
Decision: Node 24 (current LTS; Node 22 is in maintenance), pnpm 10.34.9 pinned via `packageManager`, TypeScript 6.0.x (typescript-eslint 8 supports <6.1, so not TS 7), Prisma 7.10.1 (npm `latest` points at an 8.0 RC). Consequence: Render pins `NODE_VERSION=24`; revisit TS 7 when typescript-eslint supports it.

## D10 — Prisma 7 connection config (2026-10-29)
Context: Prisma 7 dropped `url`/`directUrl` from `schema.prisma`. Decision: `packages/db/prisma.config.ts` points the CLI (migrate) at `DIRECT_URL`; the runtime client uses the pooled `DATABASE_URL` through `@prisma/adapter-pg` (`createDb()`). Same intent as D8. Consequence: generated client lives in `packages/db/src/generated` (gitignored, regenerated on install).

## D11 — Passkey spike is a standalone app (2026-10-29)
Decision: `apps/passkey-hello` (Express, in-memory, runs `.ts` with Node's type stripping, no build) deployed via `render.yaml`; rpID/origin default to Render's `RENDER_EXTERNAL_URL`. Throwaway — the real approval flow goes in services/consumer (M3).

## D12 — Passkey sign counts from synced authenticators (2026-10-29)
Context: M0 passkey spike on Render HTTPS passed on desktop Chrome (Google Password Manager passkey) and on iPhone Safari (iCloud Keychain passkey): register + login verified with `userVerified: true`, and both reported `signCount: 0` on every login. Synced passkeys don't keep a counter. Decision: the M3 sign-count check accepts 0 → 0 (stored 0, new 0); if the stored count is above 0, the new count must be strictly greater — equal or lower is rejected as a possible cloned authenticator. Record per credential whether it has ever reported a non-zero count. Consequence: clone detection only works for authenticators that count (e.g. hardware keys); synced passkeys rely on UV + origin/rpId + one-time challenge instead.

## D13 — Identity binding and fail-closed canonicalization in core schemas (2026-10-29)
Decision: `SignedOffer` requires `kid === payload.merchantAgentId`; `PaymentRequest` requires `kid` to equal every approved `consumerAgentId` (cartApproval, or mandate + cart) and `mandate.userId === cart.userId`. Violations surface as `SCHEMA_INVALID` at gate step 1. JCS throws on anything that is not plain JSON (undefined values, NaN, lone surrogates, class instances) instead of dropping it; `Hash` accepts only the canonical base64url spelling. Consequence: a registered agent can't sign under another agent's identity or re-wrap someone else's approval; builders must omit optional keys rather than set them to `undefined`.

## D14 — Domain separation; identity binding moves from schemas to signature verification (2026-10-29)
Supersedes the identity-binding part of D13. Decision: (1) `agentSig` covers `JCS({type:"payment_request", v:1, requestId, offer, authorization})`, and `verifyEnvelope` takes an `expectedType` and rejects any payload whose `type` differs, so a signature for one payload type never verifies as another. `signEnvelope` only accepts typed payloads. (2) Offers and cart approvals require `totalMinor` > 0 (qty was already > 0). The offer check rejects `now > holdUntil` with `OFFER_EXPIRED`, as well as `exp` past skew. (3) zod schemas check shape only. `verifyOfferEnvelope` returns `OFFER_SIG_INVALID` when the envelope kid, the payload's `merchantAgentId` and the registry agent disagree. `verifyPaymentRequestSig` returns `AGENT_SIG_INVALID` when the request kid differs from the registry agent or from any `consumerAgentId` in the approval. `checkMandateCartBinding` returns `MANDATE_INVALID` when mandate and cart users differ. Consequence: the gate gets the code for the failing step (§6 steps 3–4) instead of a generic `SCHEMA_INVALID`. Every signer must use `paymentRequestSigningInput`.

## D15 — Order state machine and webhook semantics (2026-10-29)
Decision: (1) `failed` is reachable only from `offered` and `authorized`, not from `captured` as SPEC §7.1's "any → failed" would allow. A captured order holds the buyer's money and leaves that state only by refund. Repeated and stale confirmations (a webhook after the API response, events out of order) are no-ops; anything else throws `InvalidTransitionError`. (2) A webhook is verified first. Then the `paypal_events` insert (`ON CONFLICT DO NOTHING`) and applying the event to the order run in one transaction: 0 rows inserted = duplicate → 200; an apply error rolls back → 500 so PayPal redelivers; an `InvalidTransitionError` → record the event, log `RECONCILE`, 200. A state conflict is never fixed by retrying, and it never triggers fulfilment or a refund automatically. (3) The DEMO_MODE simulator needs `x-demo-secret` = `DEMO_SECRET` (16+ chars), and its events reach `onOrderEvent` with `simulated: true`. (4) A POST that times out, loses its connection or gets a 5xx raises `PayPalApiError` with `maybeApplied: true`. Callers retry with the same `PayPal-Request-Id` and never void or mark failed on that error alone. Consequence: M7 stores one request id per order and operation, and adds a reconciliation table for state conflicts.

## D16 — Passkey verification shared in core; one sign count per verifier (2026-10-29)
Decision: (1) `verifyApprovalAssertion` in packages/core is used by both the wallet (consumer) and the merchant gate (§6 step 6a). Our own checks run before the library's signature check, so each failure maps to one code: challenge ≠ `hash(payload)` → `CART_HASH_MISMATCH`; missing UV → `APPROVAL_UV_MISSING`; wrong origin/rpId/type, missing UP, sign count not increasing (D12), or a bad signature → `APPROVAL_INVALID`. The challenge goes to `generateAuthenticationOptions` as hash bytes (`approvalChallenge`), because the library UTF-8-encodes string challenges and would sign a different value. (2) Each verifier keeps its own last-seen sign count: `registry_passkeys.signCount` belongs to the merchant gate, `wallet_credentials.signCount` to the wallet. A shared counter would make the merchant reject every genuine approval the wallet had already counted. (3) The wallet marks an approval approved and advances its sign count in one compare-and-set transaction, so an approval is used at most once even under concurrent requests. (4) Registration only creates a new user. Adding a passkey to an existing user needs a signed-in session, which the wallet doesn't have yet, so it is refused to prevent account takeover. Consequence: M7's gate calls the same core function against `registry_passkeys` and CAS-updates that column. A lost passkey means a new wallet user until sign-in exists.

## D17 — Mandate periods are UTC calendar buckets; ledger reserves atomically (2026-10-29)
Decision: (1) A mandate's `period` means a UTC calendar bucket: `day` = UTC date, `week` = ISO week from Monday 00:00 UTC, `month` = calendar month (`periodStart` in core). `mandate_spend` has one row per (mandate, bucket), matching SPEC §9. Known gap, accepted: the limit resets at the boundary, so up to 2 × `periodMinor` can be spent across a boundary (e.g. Sunday night, then Monday morning). (2) `reserve` is `INSERT … ON CONFLICT DO NOTHING`, then `UPDATE … SET spent = spent + amount WHERE spent ≤ limit − amount`. Postgres re-checks the WHERE after taking the row lock, so concurrent split orders can't jointly exceed the limit (proven with 4 concurrent orders on Neon in `pnpm test:db`). It runs inside the caller's transaction so a later gate failure rolls it back. Only the merchant gate writes the ledger (reserve at authorize, release on void); the wallet reads it. (3) The wallet builds every mandate field itself from a strict request (agent id from config, ids, nonce, iat/exp, `shipToHash = hash(ShipTo)`). The client can't set any of them. The human approves `hash(mandate)` with a passkey within 5 minutes, once (CAS as in D16). Item categories for scope checks come from the merchant's catalog, never from the request. (4) A mandate's passkey assertion is a stored proof that is checked again on every order. `verifyMandateApproval(…, { fresh })` enforces the sign count only at activation (`fresh: true`, wallet, CAS-stored). The gate re-checks with `fresh: false`, which verifies signature, UV, origin, rpId, user and `hash(mandate)` but not the count, and updates no sign count. Otherwise a counting authenticator's second order would be rejected. (5) `release` refuses (returns false, changes nothing) when the bucket holds less than the amount. It never clamps, because clamping would erase other orders' reservations. (6) DB-backed tests run only under `pnpm test:db` (vitest `--mode db`), against the Neon dev branch; `pnpm test` skips them. Consequence for M7: in one transaction, `checkMandateScope` → `reserve` (bucket from the gate's own clock, never `cart.iat`) → nonce insert → order row `pending_authorization` storing its `periodStart`, then commit. Call PayPal outside any transaction. On failure, void and release in the same transaction as the order's state CAS, so each order releases exactly once and no row lock is held across a network call.

## D18 — Offers: signed requests, DB prices, atomic holds, registry-anchored identity (2026-10-29)
Decision: (1) `POST /offers` takes a signed `offer_request` envelope from a consumer agent that is active in the registry, addressed to this merchant, valid for at most 120 s, and with a nonce used once. An unauthenticated endpoint would let anyone hold all stock for 10 minutes. Per agent: at most 10 units per line, 40 units held and 20 open offers, counted while the agent's registry row is locked `FOR UPDATE`, so concurrent requests can't race past the caps. (2) The request names only skus and quantities. Names and prices are read from `products` inside the same transaction that decrements stock (`UPDATE … WHERE stock ≥ qty`), stores the offer, its hash and holds, and records the nonce. Product rows are locked in sku order, so overlapping offers can't deadlock. Any failure rolls everything back. Proven on Neon: two requests for the last unit → exactly one offer; four overlapping offers in opposite sku order all succeed. (3) `exp = holdUntil = iat + 600 s`. The expiry job (every 30 s) and M7's gate each move an offer out of `open` by compare-and-set (`expired` returns stock; `used` keeps it sold), so a hold is released or consumed exactly once. (4) The merchant service resolves its own `merchantId` and `paypalMerchantId` from the registry by `MERCHANT_AGENT_ID` at startup and refuses to start if the agent or merchant is inactive or the registry public key isn't derived from `MERCHANT_AGENT_PRIVATE_KEY`. `db:seed` derives registry public keys from the configured private keys; re-running never changes a status and refuses to replace a registered key unless `SEED_ROTATE_KEYS=1`. The agent card is unsigned and carries no public key, and the catalog shows `inStock`, not counts. (5) New codes `OUT_OF_STOCK` (409) and `RATE_LIMITED` (429), for offer creation only. A replayed offer request reuses `APPROVAL_REPLAY`. (6) The wallet rejects mandates naming a merchant that isn't active in the registry (`MERCHANT_UNTRUSTED`) and returns the registry names for display. Consequence: M6's consumer agent signs offer requests with `CONSUMER_AGENT_PRIVATE_KEY`; M7's payee binding compares against the `MerchantSelf` loaded at startup; `used_nonces` grows until a cleanup by `exp` is added.

## D19 — Merchant on Render uses the Neon dev branch until M11 (2026-10-29)
Decision: `handshake-merchant` (render.yaml, region ohio, free plan) connects to the same Neon `dev` branch as local development (`DATABASE_URL` pooled, `DIRECT_URL` direct), so the live sandbox webhook check (M5) sees the registry and catalog already seeded there. The build applies committed migrations with `prisma migrate deploy`. Secrets are `sync: false` and entered in the Render dashboard; `PAYPAL_BASE_URL` (sandbox) and `DEMO_MODE=false` are pinned in render.yaml, and `NODE_ENV=production` is set only in the start command so the build still installs devDependencies. ## D20 — Wallet login sessions before the M8 UI (2026-10-30)
Context: `/chat` can spend under a mandate with no passkey prompt, so it must know who is asking. Decision: `POST /passkeys/login/options {userId}` stores a login payload `{v:1, type:"wallet_login", loginId, userId, iat, exp (2 min), nonce}` and returns WebAuthn options whose challenge is its hash; `POST /passkeys/login/verify` takes the challenge once, checks the assertion with core's `verifyApprovalAssertion` (credential bound to the user, origin, rpId, UV, sign count), advances the wallet sign count by compare-and-set, and returns a random 32-byte bearer token valid 1 hour. Only `sha256(token)` is stored (`sessions`). `/chat` takes the user from the session, never the body. Consequence: M8 adds the UI only; logout/revocation and refresh are not built yet.

## D21 — Consumer agent: the LLM picks, code decides (2026-10-30)
Decision: (1) The planner's tools are `discover_merchants`, `get_catalog`, `request_offer({merchantId, items:[{sku, qty≤10}]})`, `verify_offer({offerId})`, `checkout({offerId})`, all zod-strict, so no tool accepts an amount, payee, address, URL or approval. Signed offers stay in the chat session; the model sees summaries. (2) Merchants come only from `MERCHANT_URL` (allowlist). The agent card is a pointer: the registry must have its `merchantAgentId` active and linked to the card's `merchantId`. Every offer is verified against the registry key, and `merchantId ↔ merchantAgentId ↔ paypalMerchantId` must match the registry, else `MERCHANT_UNTRUSTED`. `checkout` re-verifies. (3) `decidePath` (code) picks the first active mandate with a stored proof that passes `checkMandateScope` (merchant, every catalog category, ship-to, per-order) and `spent + total ≤ periodMinor` for the current UTC bucket; anything else is step-up with the reasons. (4) The cart copies the offer's items, total, currency and `hash(offer)`; `exp = min(now + 300 s, holdUntil)`. The ship-to hash comes from the signed-in request's `shipTo`, else the newest mandate's. Step-up creates the approval, emits `WEB_URL/approve/:id`, and polls until approved, expired or the chat closes. The payment request is signed with `CONSUMER_AGENT_PRIVATE_KEY`; the consumer refuses to start if that key isn't the registry's. An offer is checked out at most once per chat, and at most one checkout per chat uses a mandate: later ones go to the phone, so a looping model or an injection can't repeat unattended orders. Receipts must name the request's `requestId` and `hash(offer)`. Catalog skus are shape-checked so only wrapped fields carry free text. Categories come from the merchant's unsigned catalog, so the consumer's scope check is advisory; the gate's check against its own `products` is the authoritative one. (5) Merchant text (names, categories) reaches the model only as `<untrusted>…</untrusted>` with delimiters and angle brackets stripped inside; the system prompt (`agent/prompts/system.md`) says it is data. At most 6 tool rounds and 4 calls per round; each call is logged with name and ids only. Consequence: M7's `/payments` must accept exactly this request; the gate re-checks everything (categories from its own DB), so a lying catalog can only push the consumer toward step-up or a gate rejection, never a payment outside the mandate.

## D22 — Merchant gate: checks in order, one commit, PayPal after; vault with first-time approval (2026-11-03)
Decision: (1) `verifyPaymentRequest` runs SPEC §6 steps 1–8 in order, each appending a decision, read-only. Then `GateStore.commit` writes, in one transaction: the `payment_requests` row (request id and offer unique), offer `open → used` only while `holdUntil > now`, the cart nonce keyed `(kid, "cart_approval", nonce)`, the merchant's own `registry_passkeys.signCount` CAS (6a), the ledger reservation (6b; an FK miss is `MANDATE_INVALID`), and the order (`offered`). PayPal (step 9) is called only after commit. Proven on Neon: four parallel 3000 orders against an 8000 mandate → exactly two; losers leave no rows. (2) Payee binding: the offer's `kid`, `merchantAgentId`, `merchantId` and `paypalMerchantId` must equal this merchant's registry identity, re-read on every request (a suspended merchant takes no payments). The offer must be the one we stored for this `kid`. (3) 6b reads the wallet's `mandates` row (same database, standing in for the registry): it must be `active` with the same hash, so revocation (M8) takes effect at the gate. Categories come from `products`. (4) Risk (step 8) is rules (velocity ≥ 5 orders in 10 min; unattended order > $200) plus an LLM over the order inside `<order>` delimiters, combined by severity; any unreadable reply or model error is `step_up`. On the mandate path `step_up` returns `STEP_UP_REQUIRED` before commit, so the offer stays open and the consumer re-asks the human on the phone once. On the passkey path the human already approved, so only `block` stops it. (5) PayPal, as chosen: a user's first order is created with save-wallet and answered `202` with PayPal's approve link; `POST /payments/:requestId/complete` reads the PayPal order and, once `APPROVED`, authorizes (`requestId-authorize`) and stores the vault id in `paypal_vaults` (server-side only). Later orders pay with `vault_id` and are authorized at once. A create PayPal rejected (not applied) fails the order and releases spend and stock; a maybe-applied one stays `offered` and `/complete` retries with the same request id. (6) Release (ledger + stock) happens only inside the order's status CAS transaction, so a void, a failed capture, the expiry job and a webhook can't release twice. (7) Webhooks map PayPal ids to orders and move them only through `transition`; simulated events, unknown orders, conflicts, reversals and partial refunds are written to `reconciliations`. Before verify, deliveries without PayPal's five headers or with a non-paypal.com cert URL are rejected, and each client is limited to 120 per minute. (8) The consumer's final message states the code's meaning of the receipt status; a message claiming "complete/paid/done" before capture is replaced by the code's summary. (9) Review fixes: an authorization PayPal reports other than `CREATED` holds nothing (PENDING waits, anything else fails and gives back). If the order closed before our CAS (expiry raced a late approval), the fresh authorization is voided and recorded. The expiry job asks PayPal once, with the same request ids, before failing an order still waiting, so a timed-out saved-wallet create is settled, not orphaned. Only `VAULTED` wallets are saved. Refunds are counted with an atomic increment inside the webhook transaction. `trust proxy` is 1 (Render's hop) so the webhook rate limit is per client. Consequence: capture is a merchant action (`/orders/:id/fulfil`, admin token); M8's dashboard drives it. The webhook needs `PAYMENT.CAPTURE.REVERSED` added (`pnpm paypal:webhook` reports it missing). The merchant now also needs `WEB_URL`, `WEBAUTHN_ORIGIN`, `WEBAUTHN_RP_ID`, the LLM variables and `MERCHANT_ADMIN_TOKEN`.

## D23 — Web app on one origin; credentials stay server-side; saved wallets need the payer confirmed (2026-11-03)
Decision: (1) `apps/web` (Next.js 16) is the only origin a browser talks to, and it is the WebAuthn origin and RP ID (`handshake-web.onrender.com` on Render). Route handlers forward allow-listed paths: `/api/c/*` to the consumer service and `/api/m/*` to the merchant. The wallet session token is set as an httpOnly, SameSite=Strict cookie by the login proxy and added as the bearer server-side; page JS never sees it. (2) Merchant dashboard sign-in, as chosen: the shopkeeper enters `MERCHANT_ADMIN_TOKEN` once; the web server compares it in constant time and sets an httpOnly cookie `exp.HMAC(token, exp)` (8 h), then adds the admin bearer to dashboard calls. Rotating the token signs everyone out. (3) Every wallet route is per session user; `/mandates/options` and `/mandates/verify` no longer accept a `userId`. Mandates render for approval from `GET /mandates/:id` (stored copy, options with challenge = its hash); revocation is session-only because it only removes permission, and the gate already refuses any mandate not `active`. Logout deletes the session; an approval whose chat closed becomes `cancelled` (shown as expired). (4) Saved-wallet payer check: a vault saved by a first PayPal approval is stored `unbound`, with the payer id and email PayPal reports (`payment_source.paypal.account_id` first), under a row lock so a concurrent confirm can't be overwritten. It becomes `pending` only when the order's own wallet user comes back from PayPal in their signed-in browser (the web server vouches with the admin bearer on `/paypal/return`); a phished approve link therefore can't attach a victim's PayPal to the attacker's wallet, since the attacker never holds the victim's return. It pays without a redirect only once the wallet user confirms that payer with a passkey over `hash({type:"paypal_link", userId, payerId, payerEmail, vaultRef, …})`, single use, and bound to the vault shown (`vaultRef = hash(vaultId)`); a different payer can never replace a confirmed vault. The vault id never leaves the database. (5) PayPal return/cancel URLs carry no request id: the return page posts PayPal's own `token` (order id) to `/paypal/return`, which finishes the order and answers with the status only. `/complete` and `/paypal/return` are rate-limited. (6) The approval page shows the ship-to address only if the stored address hashes to the cart's `shipToHash`. (7) The shopkeeper assistant uses `@paypal/agent-toolkit` with read-only actions (orders.get, transactions.list, disputes, shipment.get, payments.getRefunds) in sandbox; refunds are proposals that run through `POST /orders/:id/refund` only after the shopkeeper confirms. Consequence: the phone flow needs three Render services (`handshake-web`, `handshake-consumer`, `handshake-merchant`); the consumer and web need their own dashboard env values (render.yaml).


## D24 — Attack suite: one change per case against the real gate; how the injection items are tested (2026-11-04)
`tests/attacks` is a workspace package (`@handshake/attacks`, so its imports resolve). Each `NN-slug.attack.ts` starts from a fully valid signed request built by the merchant gate fixture: the real app, memory stores, a fake PayPal with a confirmed saved wallet, and the fake authenticator. It changes one thing and keeps the payload consistent; where the attacker would be the consumer agent itself, the request is re-signed with the agent key. `eval.test.ts` runs every case on a fresh harness and asserts four things: the exact code; `authorized === false` (no new PayPal authorization or create); no request id created twice; and no authorization captured twice. Two controls must authorize, plus two cases whose right outcome is an honest payment. It prints the table and rewrites `docs/EVAL.md` on a full run only. After the security review the eval also checks three things. (a) Each case's total authorizations, setup included, so an authorization in a step the case doesn't return is caught. (b) Duplicate charges, counted per offer, per order authorize and per authorization capture; PayPal-Request-Id dedupe hides repeats, so the count isn't by request id. (c) The gate's recorded reason, where several checks share a code. The suite also covers the PayPal redirect path (`/complete`). A mutation check, payee binding disabled, fails A32 and A33. The suite found no gap in the gate.
- **Item note:** the request schemas are strict. A `note` or `approved` field fails SCHEMA_INVALID, so no free text reaches the gate.
- **Address line:** the gate only ever sees `shipToHash`, so an injected or changed address fails CART_HASH_MISMATCH.
- **Merchant reply:**
  - Injected catalog text reaches the risk model inside `<order>` with angle brackets stripped.
  - If the model obeys, or replies with an extra field, prose or nothing at all, the gate steps up (STEP_UP_REQUIRED on the mandate path). A block is RISK_BLOCKED.
  - If the consumer agent obeys and buys outside its mandate, code policy asks the human and nothing is paid.
- **Webhook codes:** webhook cases report the router's outcome (`webhook:forged|duplicate|unauthorized`), since webhooks aren't gate requests.
- **Expectations that differ from a naive guess, all fail-closed:**
  - A replay with a counting passkey stops at the sign count (6a APPROVAL_INVALID) before the nonce check.
  - A voided order's offer is released (OFFER_EXPIRED).
  - Over-long approvals and a merchant id in the consumer `kid` fail the schema.

## D25 — A duplicate requestId gets its receipt only from the agent that sent it (2026-11-04)
Gate step 2 used to answer any seen `requestId` with the stored receipt before checking anything, so anyone holding a leaked request id could read the receipt: its order, PayPal ids and status. Now a duplicate gets the receipt only when two things hold. First, the request's `agentSig` verifies for an active, registered consumer agent (the step-3 check). Second, that `kid` is the agent recorded on the stored request (`payment_requests.agent_id`). Otherwise it gets the normal gate error and nothing else:
- `AGENT_SIG_INVALID` for a bad signature;
- `AGENT_UNTRUSTED` for an unknown, inactive or different agent.

The commit-race path, which loses the unique insert on `requestId`, applies the same agent match.

Security review follow-ups:
- `POST /payments/:requestId/complete`, which the consumer polls after PayPal's redirect, now takes the original signed request as its body, with the same proof. Unknown and someone else's requests both answer `UNKNOWN_REQUEST`. The PayPal-return route and the expiry job are trusted, so they call the internal `settleRequest` directly.
- A refused duplicate is logged but not written into the original request's decisions, so nobody holding only the id can add rows to a paid order's log.

Attack cases `dup-request-other-agent`, `dup-request-forged-sig`, `complete-leaked-id-unsigned` and `complete-other-agent` cover this; all four leaked the receipt before the fix.

Known remaining issues:
- Request ids are a client-chosen `req_…` of 1–64 characters, so a seen id is distinguishable from an unseen one (`AGENT_UNTRUSTED` vs. later steps). That reveals that a payment exists, not its receipt. Our consumer agent uses random 128-bit ids.
- `GET /payments/:requestId` still answers by id alone. Nothing calls it, so M10 either makes it status-only or removes it.

## D26 — Demo tools on the deployed demo; M10 hardening (2026-11-04)
**Demo tools.** The demo tools run on the deployed demo too (user's choice). That deployment uses the Neon dev branch until M11.
- `DEMO_MODE=true` and `DEMO_SECRET` are set in render.yaml for the merchant and the web service. The merchant no longer refuses DEMO_MODE when `NODE_ENV=production`. **Other M10 changes:**
- A declined-capture webhook voids the authorization after commit, through the new `afterOrderEvent` hook (never inside the dedupe transaction; genuine, new events only).
- The consumer pins each merchant URL to its first proven `merchantId`. If two URLs claim one merchant, neither is used.
- A step-up needs the full `shipTo`, because the phone must show it, not just a hash.
- Login options:
  - unknown users get decoy options (a per-process HMAC credential id; nothing stored), so verify fails like an expired login;
  - a per-user limit (5 per 2 minutes) applies to known and unknown ids alike;

- Register options sweep abandoned sign-ups (no passkey, challenge gone, older than 5 minutes) instead of creating the user only on verify, which would have needed a migration.

- An approval that expires mid-verify reports APPROVAL_EXPIRED.

- Core:

Review follow-ups (D26):
- **Reset guard:** reset also requires `DEMO_DATABASE_HOST` to equal the hostname in `DATABASE_URL`, including any `-pooler` suffix, in both the endpoint and the CLI. Moving to Neon `main` changes the host, so reset turns itself off even if DEMO_MODE stays on.
- **Reset transaction:** it is serializable and aborts if an order it didn't void is authorized.
- **Login:** every id gets the same reads, and the limit is a sliding window per id equal to the challenge lifetime, so no user has more than 5 live challenges and known and unknown ids behave alike. The decoy key comes from the consumer agent key with a domain prefix, so it survives restarts.
- **Declined capture:** a void that fails after a declined capture leaves a reconciliation row.

Accepted:
- Known users cost one extra INSERT per login.
- Anyone who knows a user id can use up that user's login window; ids are random 128-bit.

## D27 — The web origin is https://handshake-web-debi.onrender.com (2026-11-04)
