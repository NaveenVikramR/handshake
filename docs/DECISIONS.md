# Decisions (append-only)

Format: `## D<n> — title (date)` then Context / Decision / Consequence, ≤6 lines.

## D1 — Passkeys, not custom face recognition (2026-10-28)
Context: need human-in-the-loop biometric approval. Decision: WebAuthn platform authenticator (Face ID / fingerprint / Windows Hello), userVerification required. Consequence: no biometric data leaves the device; phishing-resistant; needs HTTPS + real device for demo.

## D2 — Approval bound to cart hash (2026-10-28)
Decision: WebAuthn challenge = base64url(SHA-256(JCS(cartApproval))). Consequence: any change to amount/items/address/merchant after approval invalidates the signature; merchant verifies independently against the registry public key.

## D3 — JCS + Ed25519 for agent payloads (2026-10-28)
Decision: RFC 8785 canonical JSON, Ed25519 via node:crypto. Consequence: deterministic hashes across services; small, fast signatures.

## D4 — Authorize then capture (2026-10-28)
Decision: PayPal intent AUTHORIZE; capture only after fulfillment checks; void on failure. Consequence: money held, not taken, until trust + fulfillment confirmed.

## D5 — Trust registry as shared tables (2026-10-28)
Decision: registry tables in the shared Postgres, seeded by script; pitched as PayPal-operated in production. Consequence: simple for the hackathon; documented limitation.

## D6 — LLM is escalate-only (2026-10-28)
Decision: LLM output never sets amounts or grants approval; risk inspector can only return step-up or block. Consequence: prompt injection cannot cause an unauthorized payment.

## D8 — No Docker; Neon Postgres (2026-10-28)
Context: no Docker on the dev machine. Decision: hosted Neon Postgres, `dev` branch for local work and tests, `main` for the Render deploy; Prisma `directUrl` for migrations. Consequence: needs internet to run locally; keep the production branch alive through judging (1–15 Dec).

## D7 — Vault vs per-order approval (2026-10-29)
Result: vault spike **SUCCESS** in sandbox. The user approves on PayPal once (save-with-purchase: `attributes.vault { store_in_vault: ON_SUCCESS, usage_type: MERCHANT, customer_type: CONSUMER }`); the `/authorize` response returns the vault id with status VAULTED. Later `intent: AUTHORIZE` orders with `payment_source.paypal.vault_id` come back COMPLETED with the authorization already created — no redirect, no `stored_credential` needed. Decision: agent payments use the saved PayPal wallet (vault id stored per user, server-side only); the passkey approval of the cart hash is the per-order consent. Per-order PayPal approval stays as the fallback if a vault id is missing or revoked. Consequence: needs US sandbox accounts (an India-country Business account rejected USD); the vault id is a reusable payment credential — never log or expose it in full.

## D9 — Toolchain versions (2026-10-29)
Decision: Node 24 (current LTS; Node 22 is in maintenance), pnpm 10.34.9 pinned via `packageManager`, TypeScript 6.0.x (typescript-eslint 8 supports <6.1, so not TS 7), Prisma 7.10.1 (npm `latest` points at an 8.0 RC). Consequence: Render pins `NODE_VERSION=24`; revisit TS 7 when typescript-eslint supports it.

## D10 — Prisma 7 connection config (2026-10-29)
Context: Prisma 7 dropped `url`/`directUrl` from `schema.prisma`. Decision: `packages/db/prisma.config.ts` points the CLI (migrate) at `DIRECT_URL`; the runtime client uses the pooled `DATABASE_URL` through `@prisma/adapter-pg` (`createDb()`). Same intent as D8. Consequence: generated client lives in `packages/db/src/generated` (gitignored, regenerated on install).

## D11 — Passkey spike is a standalone app (2026-10-29)
Decision: `apps/passkey-hello` (Express, in-memory, runs `.ts` with Node's type stripping, no build) deployed via `render.yaml`; rpID/origin default to Render's `RENDER_EXTERNAL_URL`. Throwaway — the real approval flow goes in services/consumer (M3).

## D12 — Passkey sign counts from synced authenticators (2026-10-29)
Context: M0 passkey spike on Render HTTPS passed on desktop Chrome (Google Password Manager passkey) and on iPhone Safari (iCloud Keychain passkey): register + login verified with `userVerified: true`, and both reported `signCount: 0` on every login. Synced passkeys don't keep a counter. Decision: the M3 sign-count check accepts 0 → 0 (stored 0, new 0); if the stored count is above 0, the new count must be strictly greater — equal or lower is rejected as a possible cloned authenticator. Record per credential whether it has ever reported a non-zero count. Consequence: clone detection only works for authenticators that count (e.g. hardware keys); synced passkeys rely on UV + origin/rpId + one-time challenge instead.

## D13 — Identity binding and fail-closed canonicalization in core schemas (2026-10-29)
Decision: `SignedOffer` requires `kid === payload.merchantAgentId`; `PaymentRequest` requires `kid` to equal every approved `consumerAgentId` (cartApproval, or mandate + cart) and `mandate.userId === cart.userId`. Violations surface as `SCHEMA_INVALID` at gate step 1. JCS throws on anything that is not plain JSON (undefined values, NaN, lone surrogates, class instances) instead of dropping it; `Hash` accepts only the canonical base64url spelling. Consequence: a registered agent can't sign under another agent's identity or re-wrap someone else's approval; builders must omit optional keys rather than set them to `undefined`.

## D14 — Domain separation; identity binding moves from schemas to signature verification (2026-10-29)
Supersedes the identity-binding part of D13. Decision: (1) `agentSig` covers `JCS({type:"payment_request", v:1, requestId, offer, authorization})`, and `verifyEnvelope` takes an `expectedType` and rejects any payload whose `type` differs, so a signature for one payload type never verifies as another. `signEnvelope` only accepts typed payloads. (2) Offers and cart approvals require `totalMinor` > 0 (qty was already > 0). The offer check rejects `now > holdUntil` with `OFFER_EXPIRED`, as well as `exp` past skew. (3) zod schemas check shape only. `verifyOfferEnvelope` returns `OFFER_SIG_INVALID` when the envelope kid, the payload's `merchantAgentId` and the registry agent disagree. `verifyPaymentRequestSig` returns `AGENT_SIG_INVALID` when the request kid differs from the registry agent or from any `consumerAgentId` in the approval. `checkMandateCartBinding` returns `MANDATE_INVALID` when mandate and cart users differ. Consequence: the gate gets the code for the failing step (§6 steps 3–4) instead of a generic `SCHEMA_INVALID`. Every signer must use `paymentRequestSigningInput`.

## D15 — Order state machine and webhook semantics (2026-10-29)
Decision: (1) `failed` is reachable only from `offered` and `authorized`, not from `captured` as SPEC §7.1's "any → failed" would allow. A captured order holds the buyer's money and leaves that state only by refund. Repeated and stale confirmations (a webhook after the API response, events out of order) are no-ops; anything else throws `InvalidTransitionError`. (2) A webhook is verified first. Then the `paypal_events` insert (`ON CONFLICT DO NOTHING`) and applying the event to the order run in one transaction: 0 rows inserted = duplicate → 200; an apply error rolls back → 500 so PayPal redelivers; an `InvalidTransitionError` → record the event, log `RECONCILE`, 200. A state conflict is never fixed by retrying, and it never triggers fulfilment or a refund automatically. (3) The DEMO_MODE simulator needs `x-demo-secret` = `DEMO_SECRET` (16+ chars), and its events reach `onOrderEvent` with `simulated: true`. (4) A POST that times out, loses its connection or gets a 5xx raises `PayPalApiError` with `maybeApplied: true`. Callers retry with the same `PayPal-Request-Id` and never void or mark failed on that error alone. Consequence: M7 stores one request id per order and operation, and adds a reconciliation table for state conflicts.

## D16 — Passkey verification shared in core; one sign count per verifier (2026-10-29)
Decision: (1) `verifyApprovalAssertion` in packages/core is used by both the wallet (consumer) and the merchant gate (§6 step 6a). Our own checks run before the library's signature check, so each failure maps to one code: challenge ≠ `hash(payload)` → `CART_HASH_MISMATCH`; missing UV → `APPROVAL_UV_MISSING`; wrong origin/rpId/type, missing UP, sign count not increasing (D12), or a bad signature → `APPROVAL_INVALID`. The challenge goes to `generateAuthenticationOptions` as hash bytes (`approvalChallenge`), because the library UTF-8-encodes string challenges and would sign a different value. (2) Each verifier keeps its own last-seen sign count: `registry_passkeys.signCount` belongs to the merchant gate, `wallet_credentials.signCount` to the wallet. A shared counter would make the merchant reject every genuine approval the wallet had already counted. (3) The wallet marks an approval approved and advances its sign count in one compare-and-set transaction, so an approval is used at most once even under concurrent requests. (4) Registration only creates a new user. Adding a passkey to an existing user needs a signed-in session, which the wallet doesn't have yet, so it is refused to prevent account takeover. Consequence: M7's gate calls the same core function against `registry_passkeys` and CAS-updates that column. A lost passkey means a new wallet user until sign-in exists.

## D17 — Mandate periods are UTC calendar buckets; ledger reserves atomically (2026-10-29)
Decision: (1) A mandate's `period` means a UTC calendar bucket: `day` = UTC date, `week` = ISO week from Monday 00:00 UTC, `month` = calendar month (`periodStart` in core). `mandate_spend` has one row per (mandate, bucket), matching SPEC §9. Known gap, accepted: the limit resets at the boundary, so up to 2 × `periodMinor` can be spent across a boundary (e.g. Sunday night, then Monday morning). (2) `reserve` is `INSERT … ON CONFLICT DO NOTHING`, then `UPDATE … SET spent = spent + amount WHERE spent ≤ limit − amount`. Postgres re-checks the WHERE after taking the row lock, so concurrent split orders can't jointly exceed the limit (proven with 4 concurrent orders on Neon in `pnpm test:db`). It runs inside the caller's transaction so a later gate failure rolls it back. Only the merchant gate writes the ledger (reserve at authorize, release on void); the wallet reads it. (3) The wallet builds every mandate field itself from a strict request (agent id from config, ids, nonce, iat/exp, `shipToHash = hash(ShipTo)`). The client can't set any of them. The human approves `hash(mandate)` with a passkey within 5 minutes, once (CAS as in D16). Item categories for scope checks come from the merchant's catalog, never from the request. (4) A mandate's passkey assertion is a stored proof that is checked again on every order. `verifyMandateApproval(…, { fresh })` enforces the sign count only at activation (`fresh: true`, wallet, CAS-stored). The gate re-checks with `fresh: false`, which verifies signature, UV, origin, rpId, user and `hash(mandate)` but not the count, and updates no sign count. Otherwise a counting authenticator's second order would be rejected. (5) `release` refuses (returns false, changes nothing) when the bucket holds less than the amount. It never clamps, because clamping would erase other orders' reservations. (6) DB-backed tests run only under `pnpm test:db` (vitest `--mode db`), against the Neon dev branch; `pnpm test` skips them. Consequence for M7: in one transaction, `checkMandateScope` → `reserve` (bucket from the gate's own clock, never `cart.iat`) → nonce insert → order row `pending_authorization` storing its `periodStart`, then commit. Call PayPal outside any transaction. On failure, void and release in the same transaction as the order's state CAS, so each order releases exactly once and no row lock is held across a network call.

## D18 — Offers: signed requests, DB prices, atomic holds, registry-anchored identity (2026-10-29)
Decision: (1) `POST /offers` takes a signed `offer_request` envelope from a consumer agent that is active in the registry, addressed to this merchant, valid for at most 120 s, and with a nonce used once. An unauthenticated endpoint would let anyone hold all stock for 10 minutes. Per agent: at most 10 units per line, 40 units held and 20 open offers, counted while the agent's registry row is locked `FOR UPDATE`, so concurrent requests can't race past the caps. (2) The request names only skus and quantities. Names and prices are read from `products` inside the same transaction that decrements stock (`UPDATE … WHERE stock ≥ qty`), stores the offer, its hash and holds, and records the nonce. Product rows are locked in sku order, so overlapping offers can't deadlock. Any failure rolls everything back. Proven on Neon: two requests for the last unit → exactly one offer; four overlapping offers in opposite sku order all succeed. (3) `exp = holdUntil = iat + 600 s`. The expiry job (every 30 s) and M7's gate each move an offer out of `open` by compare-and-set (`expired` returns stock; `used` keeps it sold), so a hold is released or consumed exactly once. (4) The merchant service resolves its own `merchantId` and `paypalMerchantId` from the registry by `MERCHANT_AGENT_ID` at startup and refuses to start if the agent or merchant is inactive or the registry public key isn't derived from `MERCHANT_AGENT_PRIVATE_KEY`. `db:seed` derives registry public keys from the configured private keys; re-running never changes a status and refuses to replace a registered key unless `SEED_ROTATE_KEYS=1`. The agent card is unsigned and carries no public key, and the catalog shows `inStock`, not counts. (5) New codes `OUT_OF_STOCK` (409) and `RATE_LIMITED` (429), for offer creation only. A replayed offer request reuses `APPROVAL_REPLAY`. (6) The wallet rejects mandates naming a merchant that isn't active in the registry (`MERCHANT_UNTRUSTED`) and returns the registry names for display. Consequence: M6's consumer agent signs offer requests with `CONSUMER_AGENT_PRIVATE_KEY`; M7's payee binding compares against the `MerchantSelf` loaded at startup; `used_nonces` grows until a cleanup by `exp` is added.

## D19 — Merchant on Render uses the Neon dev branch until M11 (2026-10-29)
Decision: `handshake-merchant` (render.yaml, region ohio, free plan) connects to the same Neon `dev` branch as local development (`DATABASE_URL` pooled, `DIRECT_URL` direct), so the live sandbox webhook check (M5) sees the registry and catalog already seeded there. The build applies committed migrations with `prisma migrate deploy`. Secrets are `sync: false` and entered in the Render dashboard; `PAYPAL_BASE_URL` (sandbox) and `DEMO_MODE=false` are pinned in render.yaml, and `NODE_ENV=production` is set only in the start command so the build still installs devDependencies. Consequence: local runs and the deployed service share one database (offers, holds, webhook events) until M11 switches Render to the Neon `main` branch, migrates and seeds it, and gives it its own agent keys.
